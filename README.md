# yt-video-saver-bot

Телеграм-бот на **aiogram 3** + **yt-dlp**: принимает ссылку на видео или
Shorts с YouTube, показывает превью и метаданные, предлагает выбрать
разрешение инлайн-кнопками и присылает скачанный файл в чат.

## Статус: MVP

Реализовано:
- приём ссылки (youtube.com/watch, youtu.be, /shorts, /live, m.youtube.com);
- сообщение с превью, названием, автором, длительностью, просмотрами;
- инлайн-кнопки с доступными разрешениями (до 1080p, только реально
  существующие для конкретного видео варианты) с примерным размером
  файла на каждой кнопке (например, "720p · ≈45.2 МБ");
- асинхронное скачивание через `asyncio.to_thread` + `asyncio.Semaphore`
  (ограничение числа одновременных загрузок);
- отправка результата пользователю;
- аккуратная обработка ошибок (приватные/удалённые видео, live-эфиры,
  превышение лимита Telegram в 50 МБ);
- **обход лимита 50 МБ** — опциональный локальный Bot API сервер
  (поднимает лимит до 2000 МБ, см. раздел "Обход лимита 50 МБ" ниже);
- **БД пользователей** (SQLite/SQLAlchemy) и **дневной лимит скачиваний**
  на пользователя (по умолчанию 5/сутки, см. `DAILY_DOWNLOAD_LIMIT`);
- **базовая аналитика** — команда `/stats` для админа: пользователи,
  скачивания за сегодня/всего, на чём отваливаются (см. раздел "Аналитика"
  ниже);
- **прогресс скачивания** — статусное сообщение показывает процент и
  прогресс-бар по мере скачивания, а если скачивание пришлось подождать
  из-за занятых слотов `MAX_CONCURRENT_DOWNLOADS` — примерную позицию в
  очереди (см. "Архитектурные заметки" ниже).

В планах (см. "Roadmap" ниже и [docs/business-plan.md](docs/business-plan.md)):
монетизация, поддержка других площадок, batch/плейлисты, субтитры.

## Требования

- Python 3.11+ (aiogram 3.x задепрекейтил поддержку 3.10)
- **ffmpeg** в `PATH` — нужен yt-dlp, чтобы склеить отдельные видео- и
  аудио-дорожки в mp4 для разрешений выше 360p.
  Проверить: `ffmpeg -version`.
  Установка на macOS: `brew install ffmpeg`.

## Установка

```bash
# Текущий venv/ создан на Python 3.10 — aiogram это уже не поддерживает,
# пересоздайте его на Python 3.11+ (проверьте версии: ls /usr/local/bin/python3.*
# или `brew install python@3.12`, если ни одной 3.11+ не установлено):

rm -rf venv
python3.11 -m venv venv        # или python3.12 — какая версия у вас есть

source venv/bin/activate
pip install -r requirements.txt          # либо requirements-dev.txt для тестов

cp .env.example .env
# открыть .env и вписать BOT_TOKEN, полученный у @BotFather;
# чтобы работала команда /stats — свой Telegram user_id в ADMIN_USER_IDS
```

## Запуск

```bash
source venv/bin/activate
python -m bot
```

Бот стартует на long polling — публичный HTTPS/домен не нужен. При первом
запуске автоматически создаётся файл БД (`bot.db` в корне проекта, путь
настраивается через `DATABASE_URL`) со всеми таблицами.

## Обход лимита 50 МБ (опционально)

Telegram Bot API по умолчанию не даёт ботам отправлять файлы крупнее
50 МБ. Чтобы снять это ограничение (до 2000 МБ), можно поднять
собственный Bot API сервер и указать боту его адрес вместо
`api.telegram.org`:

```bash
# 1. Получить api_id и api_hash на https://my.telegram.org/apps
# 2. Вписать их в .env:
#      TELEGRAM_API_ID=...
#      TELEGRAM_API_HASH=...
# 3. Поднять локальный сервер:
docker compose up -d

# 4. В .env указать боту адрес локального сервера и поднять лимит:
#      TELEGRAM_API_BASE_URL=http://localhost:8081
#      MAX_FILE_SIZE_MB=2000
# 5. Перезапустить бота (python -m bot)
```

Если `TELEGRAM_API_BASE_URL` не задан (пусто по умолчанию) — бот работает
как раньше, через обычный облачный Bot API с лимитом в 50 МБ. Подробности
и возможные дальнейшие оптимизации — в комментариях `docker-compose.yml`.

## Дневной лимит скачиваний

Каждому пользователю разрешено `DAILY_DOWNLOAD_LIMIT` успешных скачиваний
за текущие UTC-сутки (по умолчанию 5) — просто защита от злоупотреблений,
платных тарифов пока нет. При превышении бот отвечает всплывающим
уведомлением и не запускает скачивание; попытка тоже логируется в БД
(статус `blocked_daily_limit`) — это прямой сигнал платёжеспособного
спроса для будущей монетизации, см. [docs/business-plan.md](docs/business-plan.md).

Пользователи из `ADMIN_USER_IDS` полностью освобождены от этого лимита
(проверяется в `DailyLimitMiddleware` раньше подсчёта скачиваний за
сутки) — чтобы можно было свободно тестировать бота, не упираясь в 5
скачиваний и не дожидаясь полуночи по UTC.

## Аналитика

Команда `/stats` (доступна только пользователям из `ADMIN_USER_IDS` —
Telegram user_id через запятую в `.env`) показывает: всего пользователей,
новых и активных сегодня, скачиваний сегодня/всего, сколько пользователей
упёрлись в дневной лимит, и разбивку неудачных попыток сегодня по
причинам (приватное/удалённое видео, live-эфир, нет форматов, превышен
размер файла, прочая ошибка) — то есть на чём именно отваливаются
пользователи в воронке "прислал ссылку → получил видео".

## Архитектурные заметки

- **Конкурентность**: Telegram API вызовы асинхронны (aiogram), но yt-dlp —
  блокирующая библиотека. Каждое скачивание выполняется в отдельном потоке
  через `asyncio.to_thread`, а общее число одновременных скачиваний
  ограничено `asyncio.Semaphore(MAX_CONCURRENT_DOWNLOADS)`, чтобы не
  положить сервер при наплыве пользователей.
- **Хранение состояния между "выбором разрешения" и колбэком**:
  `callback_data` Telegram ограничен 64 байтами, поэтому в кнопку не
  поместить полный URL + формат. Вместо этого используется короткий
  request_id (`RequestCache`, in-memory, TTL). При масштабировании на
  несколько инстансов бота это хранилище нужно будет вынести в Redis
  или БД — сейчас это самое узкое место для горизонтального масштабирования.
  Что также иначе можно решить — уменьшить/убрать проблему хранения
  состояния целиком, синхронно перезапрашивая метаданные при колбэке
  (не потребует внешнего хранилища, но каждое нажатие кнопки будет чуть
  медленнее).
- **Временные файлы**: каждое скачивание получает свою временную папку
  (`tempfile.mkdtemp` внутри `downloads/`), которая удаляется по `finally`
  сразу после отправки видео или в случае ошибки — на диске не копится
  мусор даже при сбоях.
- **Лимит 50 МБ**: у облачного Telegram Bot API есть жёсткое ограничение
  на размер файлов, отправляемых ботами. Бот всегда скачивает видео и
  проверяет реальный размер против `MAX_FILE_SIZE_MB` (не самого факта
  превышения формального 50-мегабайтного лимита) — так предел настраивается
  в одном месте: без локального Bot API сервера ставим 50, с ним —
  например, 2000 (см. "Обход лимита 50 МБ" выше). Если файл всё равно
  больше лимита, он не отправляется (это гарантированно не сработает),
  пользователю сообщается, попытка логируется как `failed_size_limit`.
- **Размер файла на кнопках**: оценка, а не точное значение — yt-dlp
  отдаёт filesize (точный) или filesize_approx (посчитанный по битрейту и
  длительности), не всегда есть даже он — сам факт, что это approx, уже
  вносит некоторую погрешность, ей мы управлять не можем. Для
  adaptive-форматов (видео и аудио отдельными потоками, типично выше 360p)
  складываются размер видео-потока нужной высоты и лучшего аудио отдельно;
  для progressive (уже со звуком, обычно ≤360p) берётся размер как есть,
  без повторного прибавления аудио. Если данных нет вообще — кнопка просто
  без размера ("720p" без "· ≈NN МБ"), это осознанный отказ показывать
  выдуманное число, а не баг.
  Если на высоте есть несколько кандидатов (разные кодеки/контейнеры),
  предпочтение — сначала mp4/m4a (как и в `_build_format_selector`), а
  внутри этого — ПОСЛЕДНИЙ по порядку в `info["formats"]`, а НЕ самый
  большой по размеру: yt-dlp отдаёт этот список уже отсортированным от
  худшего варианта к лучшему по своему приоритету качества, так что
  последний подходящий — это и есть то, что реально выберется при
  скачивании. Раньше (до 2026-08-29) здесь стоял `max(..., key=filesize)` —
  среди нескольких вариантов на одной высоте (например VP9 и более
  компактный AV1) оценка бралась по самому тяжёлому, из-за чего цифра на
  кнопке могла заметно превышать фактический результат.
- **БД и дневной лимит**: SQLite через SQLAlchemy async + aiosqlite,
  подключение вынесено в `Database` (bot/db/engine.py) и прокидывается в
  обработчики через aiogram DI, как `config`/`semaphore` — без глобального
  состояния модуля, что упрощает тесты (tests/test_db.py создаёт отдельную
  БД на файл во временной директории). Проверка дневного лимита живёт в
  отдельном middleware (`DailyLimitMiddleware`), а не внутри обработчика —
  так обработчик скачивания не знает о лимитах вообще, а сама проверка
  переиспользуема и тестируема отдельно от Telegram-специфичного кода.
  Каждая попытка (успех, разные виды отказа, блокировка лимитом)
  логируется отдельной строкой в таблицу `events` — это и есть источник
  данных для `/stats`.
- **Прогресс скачивания**: yt-dlp зовёт `progress_hooks`/`postprocessor_hooks`
  синхронно из потока скачивания (того самого `asyncio.to_thread`), поэтому
  напрямую редактировать Telegram-сообщение оттуда нельзя — `ProgressReporter`
  (bot/services/progress_reporter.py) мостит апдейты в event loop бота через
  `asyncio.run_coroutine_threadsafe`. Апдейты троттлятся (`bot/utils/throttle.py`):
  не чаще раза в 3 секунды и только если процент заметно изменился, кроме
  смены стадии (видео → аудио → сборка ffmpeg) и завершения — это отправляется
  сразу. Без троттлинга прогресс-хук может дёргаться десятки раз в секунду и
  быстро упереться в лимиты Telegram на редактирование сообщений.
- **Позиция в очереди**: `DownloadQueue` (bot/services/download_queue.py) — это
  учёт для UI, не сам механизм ограничения конкурентности (им как и раньше
  занимается `asyncio.Semaphore(MAX_CONCURRENT_DOWNLOADS)`). Каждый запрос на
  скачивание встаёт в очередь при нажатии кнопки; если его позиция больше
  числа доступных слотов, пользователю показывается "перед вами: N" вместо
  тишины на несколько секунд, пока освободится слот. Как и `request_cache`,
  это состояние в памяти процесса — при нескольких инстансах бота его тоже
  нужно будет вынести в общее хранилище.

   абстрагирован под это); метрики и алерты.
