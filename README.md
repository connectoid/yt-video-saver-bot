# TubeDrop (yt-video-saver-bot)

Телеграм-бот **TubeDrop** (@tubedrop_bot) на **aiogram 3** + **yt-dlp**:
принимает ссылку на видео или Shorts с YouTube, показывает превью и
метаданные, предлагает выбрать разрешение инлайн-кнопками и присылает
скачанный файл в чат. Имя репозитория (`yt-video-saver-bot`) осталось
техническим — публичное имя и username бота см. ниже, раздел "Имя и
профиль бота".

## Статус: MVP

Реализовано:
- приём ссылки (youtube.com/watch, youtu.be, /shorts, /live, m.youtube.com);
- сообщение с превью, названием, автором, длительностью, просмотрами;
- инлайн-кнопки с доступными разрешениями (до 1080p, только реально
  существующие для конкретного видео варианты) с примерным размером
  файла на каждой кнопке (например, "720p · ≈45.2 МБ"), плюс кнопка
  "🎵 Скачать аудио" — лучшая доступная аудиодорожка, без перекодирования
  в mp3 и без размера на кнопке;
- асинхронное скачивание через `asyncio.to_thread` + `asyncio.Semaphore`
  (ограничение числа одновременных загрузок);
- отправка результата пользователю;
- аккуратная обработка ошибок (приватные/удалённые видео, live-эфиры,
  превышение лимита Telegram в 50 МБ);
- **обход лимита 50 МБ** — опциональный локальный Bot API сервер
  (поднимает лимит до 2000 МБ, см. раздел "Обход лимита 50 МБ" ниже);
- **БД пользователей** (SQLite/SQLAlchemy) и **дневной лимит скачиваний**
  на пользователя (по умолчанию 5/сутки, см. `DAILY_DOWNLOAD_LIMIT`);
- **базовая аналитика** — команда `/stats` для админа: пользователи,
  скачивания за сегодня/всего, на чём отваливаются (см. раздел "Аналитика"
  ниже);
- **прогресс скачивания** — статусное сообщение показывает процент и
  прогресс-бар по мере скачивания, а если скачивание пришлось подождать
  из-за занятых слотов `MAX_CONCURRENT_DOWNLOADS` — примерную позицию в
  очереди (см. "Архитектурные заметки" ниже);
- **командное меню** — `/start`, `/help`, `/limits`, `/history`, `/cancel`,
  `/terms`, `/feedback` для всех, плюс `/stats` отдельно только в меню
  `ADMIN_USER_IDS` (см. раздел "Команды" ниже);
- **предпосылки для монетизации (фаза 2 бизнес-плана)** — условия
  использования (`/terms`) и блок-лист video_id по запросу правообладателя
  (`/block`, `/unblock`, `/blocklist` для админа), см. разделы "Команды" и
  "Архитектурные заметки" ниже;
- **обратная связь (`/feedback`)** — пользователь одним сообщением (текстом
  или, например, скриншотом) пишет администратору: пожелание, баг, жалоба —
  бот пересылает его всем `ADMIN_USER_IDS`, см. разделы "Команды" и
  "Архитектурные заметки" ниже.

В планах (см. "Roadmap" ниже и [docs/business-plan.md](docs/business-plan.md)):
монетизация, поддержка других площадок, batch/плейлисты, субтитры.

## Требования

- Python 3.11+ (aiogram 3.x задепрекейтил поддержку 3.10)
- **ffmpeg** в `PATH` — нужен yt-dlp, чтобы склеить отдельные видео- и
  аудио-дорожки в mp4 для разрешений выше 360p.
  Проверить: `ffmpeg -version`.
  Установка на macOS: `brew install ffmpeg`.

## Установка

```bash
# Текущий venv/ создан на Python 3.10 — aiogram это уже не поддерживает,
# пересоздайте его на Python 3.11+ (проверьте версии: ls /usr/local/bin/python3.*
# или `brew install python@3.12`, если ни одной 3.11+ не установлено):

rm -rf venv
python3.11 -m venv venv        # или python3.12 — какая версия у вас есть

source venv/bin/activate
pip install -r requirements.txt          # либо requirements-dev.txt для тестов

cp .env.example .env
# открыть .env и вписать BOT_TOKEN, полученный у @BotFather;
# чтобы работала команда /stats — свой Telegram user_id в ADMIN_USER_IDS
```

## Запуск

```bash
source venv/bin/activate
python -m bot
```

Бот стартует на long polling — публичный HTTPS/домен не нужен. При первом
запуске автоматически создаётся файл БД (`bot.db` в корне проекта, путь
настраивается через `DATABASE_URL`) со всеми таблицами.

## Обход лимита 50 МБ (опционально)

Telegram Bot API по умолчанию не даёт ботам отправлять файлы крупнее
50 МБ. Чтобы снять это ограничение (до 2000 МБ), можно поднять
собственный Bot API сервер и указать боту его адрес вместо
`api.telegram.org`:

```bash
# 1. Получить api_id и api_hash на https://my.telegram.org/apps
# 2. Вписать их в .env:
#      TELEGRAM_API_ID=...
#      TELEGRAM_API_HASH=...
# 3. Поднять локальный сервер:
docker compose up -d

# 4. В .env указать боту адрес локального сервера и поднять лимит:
#      TELEGRAM_API_BASE_URL=http://localhost:8081
#      MAX_FILE_SIZE_MB=2000
# 5. Перезапустить бота (python -m bot)
```

Если `TELEGRAM_API_BASE_URL` не задан (пусто по умолчанию) — бот работает
как раньше, через обычный облачный Bot API с лимитом в 50 МБ. Подробности
и возможные дальнейшие оптимизации — в комментариях `docker-compose.yml`.

## Дневной лимит скачиваний

Каждому пользователю разрешено `DAILY_DOWNLOAD_LIMIT` успешных скачиваний
за текущие UTC-сутки (по умолчанию 5) — просто защита от злоупотреблений,
платных тарифов пока нет. При превышении бот отвечает всплывающим
уведомлением и не запускает скачивание; попытка тоже логируется в БД
(статус `blocked_daily_limit`) — это прямой сигнал платёжеспособного
спроса для будущей монетизации, см. [docs/business-plan.md](docs/business-plan.md).

Пользователи из `ADMIN_USER_IDS` полностью освобождены от этого лимита
(проверяется в `DailyLimitMiddleware` раньше подсчёта скачиваний за
сутки) — чтобы можно было свободно тестировать бота, не упираясь в 5
скачиваний и не дожидаясь полуночи по UTC.

## Имя и профиль бота

Бот называется **TubeDrop**, username — **@tubedrop_bot**. Профиль состоит
из трёх частей, и Bot API умеет менять только две из них:

- **Отображаемое имя** ("TubeDrop"), **About** (короткое описание на
  странице профиля и в превью при пересылке ссылки на бота) и
  **Description** (текст в пустом чате до нажатия "Старт") — заданы в
  коде, `bot/profile.py` (`BOT_NAME`/`BOT_SHORT_DESCRIPTION`/
  `BOT_DESCRIPTION` + функция `set_bot_profile()`), но применяются
  **вручную, один раз**, а не автоматически при каждом старте бота.
  Раньше `set_bot_profile()` вызывалась из `bot/main.py` при каждом
  запуске — оказалось, что `setMyName` (в отличие от `setMyCommands`) у
  Telegram под отдельным жёстким флуд-контролем, и частые перезапуски
  при деплое упёрлись в `TelegramRetryAfter` на несколько часов. Чтобы
  применить/обновить профиль — запустить один раз вручную, например:
  ```bash
  python -c "
  import asyncio
  from aiogram import Bot
  from bot.config import load_config
  from bot.profile import set_bot_profile

  async def main():
      config = load_config()
      bot = Bot(token=config.bot_token)
      await set_bot_profile(bot)
      await bot.session.close()

  asyncio.run(main())
  "
  ```
  или вручную через @BotFather (`/setname`, `/setabouttext`,
  `/setdescription`) — это то же самое поле Bot API, способы
  взаимозаменяемы.
- **Username** (`@tubedrop_bot`) Bot API менять не умеет вообще — это
  разовая ручная настройка через @BotFather: `/setusername`, выбрать
  бота, ввести `tubedrop_bot` (проверьте, что имя свободно — @BotFather
  откажет, если оно занято).

## Команды

Публичное меню бота (иконка "/" рядом с полем ввода в Telegram, задаётся
через `bot.set_my_commands()` при старте — см. `bot/commands.py`). У
каждого из `ADMIN_USER_IDS` меню чуть шире — см. "Админ-меню" в конце
этого раздела.

- `/start`, `/help` — знакомство и краткая инструкция.
- `/limits` — сколько скачиваний осталось сегодня (или "лимита нет", если
  вызвавший — админ из `ADMIN_USER_IDS`).
- `/history` — последние (до 10) успешно скачанных видео: название
  (кликабельная ссылка на youtu.be), разрешение, реальный размер файла и
  дата. Только успешные скачивания — ни неудачные попытки, ни отменённые
  сюда не попадают.
- `/cancel` — прерывает текущее скачивание пользователя, если оно сейчас
  идёт (качается или ждёт своей очереди/слота в семафоре). Работает в две
  ступени: `asyncio.Task.cancel()` прерывает асинхронную часть (ожидание
  слота, отправку файла в Telegram), а отдельный `threading.Event`
  (`cancel_event`) сигналит самому потоку yt-dlp остановиться на
  ближайшем progress-хуке, а не докачивать всё до конца впустую в фоне —
  подробнее в "Архитектурные заметки" ниже.
- `/terms` — условия использования (ответственность пользователя за
  авторские права, какие данные хранятся, право закрыть доступ к видео по
  жалобе правообладателя). Ссылка на неё есть в `/start`.
- `/feedback` — написать администратору: бот сначала показывает, что можно
  прислать (пожелание по функциям, баг, жалоба, можно со скриншотом; отдельно
  отмечено — если видео скачалось неправильно/не воспроизводится/не
  скачалось вовсе, прислать ссылку на него, чтобы можно было воспроизвести
  и починить), затем пересылает СЛЕДУЮЩЕЕ сообщение пользователя всем
  `ADMIN_USER_IDS` через `message.forward()` — подробнее в "Архитектурные
  заметки" ниже.

`/block`, `/unblock`, `/blocklist` в это меню намеренно не входят вообще ни у
кого — см. "Блок-лист видео" ниже.

### Админ-меню

У каждого пользователя из `ADMIN_USER_IDS` в меню команд, помимо всего
перечисленного выше, есть ещё и `/stats` (см. "Аналитика" ниже) — только у
него, обычным пользователям эта команда не показывается. Технически это
отдельный список команд с `BotCommandScopeChat(chat_id=admin_id)` —
персональный скоуп Telegram Bot API, применяется поверх общего публичного
меню персонально на chat_id каждого админа (`bot/commands.py:
set_bot_commands()`). Чтобы это сработало, админ должен хотя бы раз до этого
написать боту (`/start`) — иначе Telegram ещё не знает такого чата и
вернёт ошибку; это не баг, а нормальная ситуация для только что добавленного
в `ADMIN_USER_IDS` id — админ-меню применится при следующем перезапуске
бота после первого `/start`.

## Аналитика

Команда `/stats` (доступна только пользователям из `ADMIN_USER_IDS` —
Telegram user_id через запятую в `.env`, и только у них видна в меню команд,
см. "Админ-меню" выше) показывает: всего пользователей,
новых и активных сегодня, скачиваний сегодня/всего (сегодняшняя цифра — с
разбивкой, сколько из них через кнопку "Скачать аудио"), сколько пользователей
упёрлись в дневной лимит, сколько скачиваний сегодня отменили сами
пользователи (`/cancel`), и разбивку неудачных попыток сегодня по
причинам (приватное/удалённое видео, live-эфир, нет форматов, превышен
размер файла, прочая ошибка), сколько раз сегодня запрашивали видео из
блок-листа, сколько сообщений сегодня отправили через `/feedback` — то есть
на чём именно отваливаются пользователи в воронке "прислал ссылку → получил
видео". Отменённые скачивания, запросы заблокированных видео и сообщения
через `/feedback` в разбивку по причинам не попадают — это не сбой бота, а
осознанные события, каждое считается отдельной строкой.

Отдельная строка — "Язык клиента не RU": доля пользователей, у которых
Telegram-клиент настроен не на русский (`User.language_code`, IETF-код вроде
"en"/"uk", не выбор языка внутри бота — локализации у бота пока нет). Это
данные для решения "стоит ли делать RU/EN-локализацию" — см. "Архитектурные
заметки" ниже.

## Блок-лист видео

По запросу правообладателя (или другой причине) конкретное видео можно
закрыть для скачивания — это работает через таблицу `blocked_videos` в БД
и три админ-команды (доступны только `ADMIN_USER_IDS`, как и `/stats`):

- `/block <video_id> [причина]` — добавить видео в блок-лист. Причина
  необязательна, но полезна, чтобы через месяц вспомнить, зачем оно там.
- `/unblock <video_id>` — убрать видео из блок-листа.
- `/blocklist` — показать текущий список.

`video_id` — это 11-символьный id из ссылки YouTube (то, что после `v=`
или после `/shorts/`), не сама ссылка целиком. Проверка блок-листа
выполняется до похода в yt-dlp за метаданными (см. "Архитектурные
заметки" ниже) и применяется сразу же, без перезапуска бота — это и есть
весь смысл держать список в БД, а не в конфиге: при реальной жалобе
правообладателя счёт может идти на минуты.

## Архитектурные заметки

- **Конкурентность**: Telegram API вызовы асинхронны (aiogram), но yt-dlp —
  блокирующая библиотека. Каждое скачивание выполняется в отдельном потоке
  через `asyncio.to_thread`, а общее число одновременных скачиваний
  ограничено `asyncio.Semaphore(MAX_CONCURRENT_DOWNLOADS)`, чтобы не
  положить сервер при наплыве пользователей.
- **Хранение состояния между "выбором разрешения" и колбэком**:
  `callback_data` Telegram ограничен 64 байтами, поэтому в кнопку не
  поместить полный URL + формат. Вместо этого используется короткий
  request_id (`RequestCache`, in-memory, TTL). При масштабировании на
  несколько инстансов бота это хранилище нужно будет вынести в Redis
  или БД — сейчас это самое узкое место для горизонтального масштабирования.
  Что также иначе можно решить — уменьшить/убрать проблему хранения
  состояния целиком, синхронно перезапрашивая метаданные при колбэке
  (не потребует внешнего хранилища, но каждое нажатие кнопки будет чуть
  медленнее).
- **Временные файлы**: каждое скачивание получает свою временную папку
  (`tempfile.mkdtemp` внутри `downloads/`), которая удаляется по `finally`
  сразу после отправки видео или в случае ошибки — на диске не копится
  мусор даже при сбоях.
- **Лимит 50 МБ**: у облачного Telegram Bot API есть жёсткое ограничение
  на размер файлов, отправляемых ботами. Бот всегда скачивает видео и
  проверяет реальный размер против `MAX_FILE_SIZE_MB` (не самого факта
  превышения формального 50-мегабайтного лимита) — так предел настраивается
  в одном месте: без локального Bot API сервера ставим 50, с ним —
  например, 2000 (см. "Обход лимита 50 МБ" выше). Если файл всё равно
  больше лимита, он не отправляется (это гарантированно не сработает),
  пользователю сообщается, попытка логируется как `failed_size_limit`.
- **Размер файла на кнопках**: оценка, а не точное значение — yt-dlp
  отдаёт filesize (точный) или filesize_approx (посчитанный по битрейту и
  длительности), не всегда есть даже он — сам факт, что это approx, уже
  вносит некоторую погрешность, ей мы управлять не можем. Для
  adaptive-форматов (видео и аудио отдельными потоками, типично выше 360p)
  складываются размер видео-потока нужной высоты и лучшего аудио отдельно;
  для progressive (уже со звуком, обычно ≤360p) берётся размер как есть,
  без повторного прибавления аудио. Если данных нет вообще — кнопка просто
  без размера ("720p" без "· ≈NN МБ"), это осознанный отказ показывать
  выдуманное число, а не баг.
  Если на высоте есть несколько кандидатов (разные кодеки/контейнеры),
  предпочтение — сначала mp4/m4a (как и в `_build_format_selector`), а
  внутри этого — ПОСЛЕДНИЙ по порядку в `info["formats"]`, а НЕ самый
  большой по размеру: yt-dlp отдаёт этот список уже отсортированным от
  худшего варианта к лучшему по своему приоритету качества, так что
  последний подходящий — это и есть то, что реально выберется при
  скачивании. Раньше (до 2026-08-29) здесь стоял `max(..., key=filesize)` —
  среди нескольких вариантов на одной высоте (например VP9 и более
  компактный AV1) оценка бралась по самому тяжёлому, из-за чего цифра на
  кнопке могла заметно превышать фактический результат.
- **БД и дневной лимит**: SQLite через SQLAlchemy async + aiosqlite,
  подключение вынесено в `Database` (bot/db/engine.py) и прокидывается в
  обработчики через aiogram DI, как `config`/`semaphore` — без глобального
  состояния модуля, что упрощает тесты (tests/test_db.py создаёт отдельную
  БД на файл во временной директории). Проверка дневного лимита живёт в
  отдельном middleware (`DailyLimitMiddleware`), а не внутри обработчика —
  так обработчик скачивания не знает о лимитах вообще, а сама проверка
  переиспользуема и тестируема отдельно от Telegram-специфичного кода.
  Каждая попытка (успех, разные виды отказа, блокировка лимитом)
  логируется отдельной строкой в таблицу `events` — это и есть источник
  данных для `/stats`.
- **Прогресс скачивания**: yt-dlp зовёт `progress_hooks`/`postprocessor_hooks`
  синхронно из потока скачивания (того самого `asyncio.to_thread`), поэтому
  напрямую редактировать Telegram-сообщение оттуда нельзя — `ProgressReporter`
  (bot/services/progress_reporter.py) мостит апдейты в event loop бота через
  `asyncio.run_coroutine_threadsafe`. Апдейты троттлятся (`bot/utils/throttle.py`):
  не чаще раза в 3 секунды и только если процент заметно изменился, кроме
  смены стадии (видео → аудио → сборка ffmpeg) и завершения — это отправляется
  сразу. Без троттлинга прогресс-хук может дёргаться десятки раз в секунду и
  быстро упереться в лимиты Telegram на редактирование сообщений.
- **Позиция в очереди**: `DownloadQueue` (bot/services/download_queue.py) — это
  учёт для UI, не сам механизм ограничения конкурентности (им как и раньше
  занимается `asyncio.Semaphore(MAX_CONCURRENT_DOWNLOADS)`). Каждый запрос на
  скачивание встаёт в очередь при нажатии кнопки; если его позиция больше
  числа доступных слотов, пользователю показывается "перед вами: N" вместо
  тишины на несколько секунд, пока освободится слот. Как и `request_cache`,
  это состояние в памяти процесса — при нескольких инстансах бота его тоже
  нужно будет вынести в общее хранилище.
- **Отмена скачивания (/cancel)**: `active_downloads` (bot/handlers/video.py)
  хранит на каждого пользователя пару (asyncio.Task, threading.Event) для его
  текущего скачивания. Отмена — в два шага, потому что скачивание живёт сразу
  в двух мирах: `task.cancel()` прерывает asyncio-часть (ожидание слота в
  семафоре/очереди, отправку файла в Telegram), а вот сам yt-dlp работает
  внутри `asyncio.to_thread` — это отдельный OS-поток, который `task.cancel()`
  НЕ останавливает (Python не может форсированно прибить поток; отменяется
  только ожидание его результата). Поэтому дополнительно взводится
  `cancel_event` (`threading.Event`) — прогресс- и postprocessor-хуки
  yt-dlp (см. "Прогресс" выше) проверяют его при каждом вызове и поднимают
  `yt_dlp.utils.DownloadCancelled`, если он взведён — это официальный
  способ yt-dlp прервать скачивание изнутри хука. Без этого механизма
  скачивание продолжалось бы в фоне вхолостую (тратя канал/CPU и удерживая
  ffmpeg) уже после того, как пользователь и бот о нём "забыли". Известное
  ограничение: если `cancel_event` взводится ровно в момент, когда уже
  запущен сам процесс ffmpeg (слияние видео+аудио), прервать сам ffmpeg
  так нельзя — но эта стадия обычно занимает секунды.
- **История (/history)**: событие `download`/`success` в таблице `events`
  теперь хранит ещё и `title` — понадобилось добавить колонку в уже
  существующую (задеплоенную) таблицу, `Base.metadata.create_all` умеет
  создавать только отсутствующие ТАБЛИЦЫ целиком, а не добавлять колонки в
  существующие. Поэтому в `Database.create_all()` (bot/db/engine.py) перед
  create_all добавлен маленький шаг миграции: `ALTER TABLE events ADD
  COLUMN title ...`, если такой колонки ещё нет (проверяется через
  `sqlalchemy.inspect`). Полноценной системы миграций (Alembic) в проекте
  нет — для одной SQLite-таблицы это оверкилл, а такие ALTER безопасны
  (всегда NULLABLE-колонка; старые строки, скачанные ещё до этого
  изменения, всё равно попадут в `/history` — просто вместо названия
  видео там будет плейсхолдер "Видео", `title = NULL` не ломает чтение).
- **Индекс под /history**: `get_recent_downloads()` фильтрует по
  `user_id` и сортирует по `created_at` — под этот доступ (не под
  дневной лимит/аналитику, у них своя логика) добавлен составной индекс
  `(user_id, created_at)` (`Event.__table_args__`, bot/db/models.py).
  Без него SQLite мог бы пойти по одному из уже существующих
  одноколоночных индексов (например, по `created_at`, раз нужна
  сортировка) и просматривать вглубь БД лишние строки ДРУГИХ
  пользователей, пока не наберёт 10 подходящих записей именно этого
  юзера — с ростом общего числа пользователей это стало бы всё заметнее.
  Проверено `EXPLAIN QUERY PLAN`: оптимизатор SQLite реально выбирает
  этот составной индекс для запроса `/history`. Как и с колонкой `title`
  выше — на уже существующей БД сам индекс не появится сам по себе,
  поэтому та же миграция в `Database.create_all()` дополнительно делает
  `CREATE INDEX IF NOT EXISTS ix_events_user_id_created_at ...` (для
  индексов, в отличие от колонок, SQLite сам поддерживает `IF NOT
  EXISTS`, отдельная проверка через `sqlalchemy.inspect` не нужна).
- **ToS + блок-лист video_id (предпосылки фазы 2)**: перед тем как
  переходить к монетизации (Stars, платные тарифы, батч/плейлисты — см.
  [docs/business-plan.md](docs/business-plan.md)), сделаны два дешёвых
  сейчас и дорогих "в панике после жалобы" шага. `BlockedVideo` — НОВАЯ
  таблица (`bot/db/models.py`), поэтому отдельной миграции колонок/индексов
  в `bot/db/engine.py` не потребовалось — `Base.metadata.create_all` создаёт
  целиком отсутствующие таблицы сам. Проверка блок-листа устроена в два
  слоя: (1) в `handle_link` (`bot/handlers/video.py`) — по `video_id`,
  извлечённому регуляркой из самой ссылки (`extract_video_id`,
  `bot/utils/url_utils.py`), **до** похода в yt-dlp за метаданными, чтобы
  не тратить время/ресурсы на заведомо отклонённое видео; (2) повторно в
  `handle_resolution_choice` — редкий, но реальный случай, когда кнопки
  разрешений уже были показаны пользователю в момент, когда админ
  заблокировал видео: без этой второй проверки блокировка применялась бы
  только к новым запросам, а не немедленно. Обе проверки fail-open: если
  БД временно недоступна, видео считается НЕ заблокированным (тот же
  принцип, что и в `DailyLimitMiddleware` для дневного лимита) — блок-лист
  защищает от юридических рисков, а не от злоупотреблений, отказывать в
  обслуживании из-за временного сбоя БД ради него не стоит. `/terms`
  (`bot/handlers/common.py`, текст — `build_terms_text` в
  `bot/utils/formatting.py`) — без юридической вычитки, базовый набросок;
  контакт для жалоб на авторские права необязателен и настраивается через
  `SUPPORT_CONTACT` в `.env`, при пустом значении используется общая
  формулировка "пишите администратору".
- **`User.language_code` — данные под решение о локализации**: пользователь
  спросил, стоит ли уже добавлять RU/EN-переключение языка — ответ был "пока
  рано" (нет запущенного продукта, вся текущая аудитория и бизнес-план
  завязаны на русскоязычных пользователей, сама локализация — не
  косметика, а слой переводов под весь пользовательский текст + хранение
  языка + переключатель), но решение стоит принимать по данным, а не
  вслепую. Добавлена колонка `User.language_code` (bot/db/models.py) — IETF-код
  языка Telegram-КЛИЕНТА пользователя (`update.from_user.language_code`, то,
  что сам Telegram присылает на каждый апдейт), не выбор языка внутри бота.
  Пишется/обновляется в `UserActivityMiddleware` вместе с username/full_name —
  апдейт, а не только при создании, чтобы со временем подхватывать смену
  языка клиента, а не застревать на значении с первого сообщения. `/stats`
  показывает разбивку: сколько пользователей ВСЕГО (не только сегодня — это
  медленно меняющийся срез аудитории, не однодневное событие) с известным
  language_code не-RU, и сколько ещё неизвестно (либо ещё не писали боту
  после появления колонки, либо Telegram не прислал значение). Через
  какое-то время работы бота эта строка даст содержательный ответ на
  исходный вопрос про локализацию.
- **Админ-меню (`/stats` только у админов)**: Telegram Bot API умеет
  показывать РАЗНЫЙ список команд в зависимости от того, кто смотрит меню —
  через параметр `scope` у `setMyCommands`. `bot/commands.py: set_bot_commands()`
  сначала задаёт общий список (`PUBLIC_COMMANDS`, дефолтный скоуп — для всех,
  у кого нет более специфичного), затем для каждого id из `ADMIN_USER_IDS`
  отдельным вызовом с `BotCommandScopeChat(chat_id=admin_id)` задаёт
  `ADMIN_COMMANDS` (= `PUBLIC_COMMANDS` + `/stats`) — Telegram показывает такой
  список ВМЕСТО дефолтного именно в чате этого админа, у всех остальных
  пользователей ничего не меняется. `ADMIN_COMMANDS` построен как
  `[*PUBLIC_COMMANDS, /stats]`, а не отдельный список с нуля — так он не может
  незаметно разойтись с публичным меню. Персональный скоуп требует, чтобы
  Telegram уже знал такой чат (админ хотя бы раз написал боту, обычно `/start`)
  — если нет, `setMyCommands` для этого id падает с `TelegramBadRequest`
  ("chat not found"); каждый админ обрабатывается в своём `try/except`, чтобы
  это не мешало ни остальным админам, ни самому запуску бота — применится
  само собой при следующем перезапуске после первого `/start` этого админа.
- **`/help` — устаревший текст про лимит 50 МБ**: текст команды был написан ещё до фазы 1 (обход через локальный Bot API сервер) и годами хардкодил "⚠️ ...файлы крупнее 50 МБ. Обход этого лимита в разработке" — уже неверно после фазы 1: обход реализован и опционален, а реальный лимит настраивается через `MAX_FILE_SIZE_MB`. Заметили при разборе того, что показывается пользователю. Исправлено: `bot/utils/formatting.py: format_file_limit_note(config)` читает реальный `config.max_file_size_mb` и (если задан `TELEGRAM_API_BASE_URL`, т.е. поднят локальный сервер) убирает формулировку "ограничение Telegram" — вместо статичной строки `HELP_TEXT` теперь `HELP_TEXT_HEADER` + вызов этой функции, `cmd_help` получает `config` через обычную aiogram DI (тот же паттерн, что и `/limits`).
- **`/feedback`**: FSM-состояние (`FeedbackStates.waiting_for_message`,
  `aiogram.fsm`, стандартный `MemoryStorage` — отдельно настраивать не
  пришлось, это дефолт `Dispatcher()`) + отдельный `outer_middleware`
  (`FeedbackCaptureMiddleware`, bot/middlewares/feedback_capture.py), а НЕ
  хендлер со `StateFilter` внутри роутера. Middleware смотрит на КАЖДОЕ
  входящее сообщение раньше любых роутеров — так порядок регистрации
  роутеров/хендлеров не влияет на то, что "выигрывает": команда или
  перехват фидбека, и не нужно вручную прокидывать `SkipHandler` (он есть в
  aiogram, но не часть публичного API — импортируется из внутреннего
  `aiogram.dispatcher.event.bases`, поэтому сознательно не используется).
  Регистрируется ПОСЛЕ `UserActivityMiddleware` (bot/main.py) — апсерт
  пользователя должен отработать даже для перехваченных сообщений.
  Захват — РАЗОВЫЙ: состояние сбрасывается сразу после первого же
  сообщения любого типа (текст, фото, документ — `message.forward()`
  пересылает как есть, без пересборки), или сразу же, если это оказалась
  команда (тогда просто передаём выполнение дальше как обычно, ничего не
  улетает админу). Без этого ссылка на видео, присланная значительно позже
  (пользователь забыл, что недавно вызывал `/feedback`), могла бы случайно
  уйти админу вместо обычной обработки — разовость держит это окно риска в
  ровно одно сообщение. Каждому админу из `ADMIN_USER_IDS` сначала уходит
  текстовая "шапка" с `tg://user?id=...`-упоминанием отправителя (подстраховка
  на случай, если у автора в настройках приватности скрыт заголовок
  "Forwarded from"), затем само сообщение через `forward()`; сбой пересылки
  одному админу (например, если он когда-то заблокировал бота) не мешает
  дойти до остальных — каждая отправка в своём `try/except`. По выбору
  (сделан вместе с автором) — связь одностороняя: ответить пользователю
  прямо через бота нельзя, админ отвечает вне Telegram-бота (в личку и т.п.).
- **Кнопка "Скачать аудио"**: рядом с кнопками разрешений — отдельная
  кнопка `dla:{request_id}` (`bot/keyboards/resolution.py`), качающая
  `AUDIO_FORMAT_SELECTOR = "bestaudio/best"` (`bot/services/ytdlp_service.py`)
  — лучшую доступную аудиодорожку БЕЗ перекодирования в mp3: `download_video`/
  `_download_sync` теперь принимают `merge_output_format` (по умолчанию
  `"mp4"`, как раньше), для аудио передаётся `None` — yt-dlp не запускает
  ffmpeg вообще, файл уходит как есть (m4a либо webm/opus — Telegram
  принимает и то, и то через `send_audio`, официальная рекомендация
  "только mp3/m4a" касается красивого отображения в плеере, а не того,
  отправится ли файл). Кнопка сознательно без размера/деталей — просто
  "🎵 Скачать аудио" (решение автора). Общая логика скачивания видео и
  аудио вынесена в `_perform_download()` (`bot/handlers/video.py`,
  параметризована `height: int | None` — `None` значит аудио), чтобы не
  дублировать обработку очереди/семафора/`/cancel`/ошибок между
  `handle_resolution_choice` и новым `handle_audio_choice`. В аналитике
  `Event.height IS NULL` на `DOWNLOAD`/`SUCCESS` однозначно значит "это
  была кнопка аудио" (видео всегда логируется с конкретным height) — на
  этом строится `Stats.audio_downloads_success_today`
  (`bot/db/crud.py::get_stats`), показывается в `/stats` рядом с обычным
  "Скачано сегодня". Упоминание кнопки добавлено в `/start` и `/help`.

## Roadmap

Бизнес-контекст (аудитория, монетизация, конкуренты, юридические риски) — в [docs/business-plan.md](docs/business-plan.md). Ниже — техническая часть, фаза 1 (обход 50 МБ, БД, лимиты, аналитика) реализована.

1. ~~Обход лимита 50 МБ~~ — готово (локальный Bot API сервер, опционально).
2. ~~База пользователей и дневные лимиты скачиваний~~ — готово (SQLite,
   `DAILY_DOWNLOAD_LIMIT`).
3. ~~Базовая аналитика~~ — готово (`/stats` для админа).
4. ~~Предпосылки для монетизации (фаза 2, шаг 1)~~ — готово: `/terms` и
   блок-лист video_id (`/block`, `/unblock`, `/blocklist`).
5. **Монетизация (фаза 2, шаг 2).** Telegram Stars как пакеты
   кредитов (не подписка — Stars не поддерживает автопродление),
   платный тариф без дневного лимита и/или с приоритетной очередью.
6. **Расширение продукта (фаза 3).** Другие площадки (TikTok, Instagram
   Reels), извлечение аудио отдельным вариантом, субтитры, обрезка по
   таймкодам, batch/плейлисты.
7. Дальше — по мере роста нагрузки: очередь задач (Celery/RQ + Redis)
   вместо in-process семафора, если понадобится несколько воркеров/машин;
   миграция БД на PostgreSQL (connection string в `DATABASE_URL` уже
   абстрагирован под это); метрики и алерты.
